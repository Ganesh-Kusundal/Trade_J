- Three-layer internal structure: `api` (REST controllers exposing replay control and analytics queries), `lab` (backtesting services and DuckDB persistence), and `core` (domain records like `ResearchSession`, `RunResult`, `StrategyConfig`).
- `research/api` depends on `research-lab` and `replay-engine` to bridge UI requests to the replay controller and DuckDB-backed analytics (`ReplayApiController.java`, `ResearchAnalyticsApiController.java`).
- `research/lab` contains the execution engines: `StrategyLabService` rolls through historical candles invoking `GraphStrategyPlugin` strategies, `ScannerLabService` evaluates `ScanCriterion` pipelines over rolling windows, and `DuckDbResearchStore` manages a persistent file-based DuckDB connection with schema initialization for `run_results`, `trade_log`, `scanner_hits`, and `candles` tables.
- `mcp-server` exposes a JSON-RPC-over-SSE Model Context Protocol endpoint (`McpServerController.java`) that delegates read-only tool calls to the same `DuckDbResearchStore`, `ReplayController`, and `DuckDbAnalyticsEngine` shared by the REST API layer.
- Dependency direction flows inward: `api` → `lab` → `core`; both `api` and `mcp-server` depend on `lab` for data access but not vice versa. Build manifests confirm cross-module dependencies via Gradle project references (`research/api/build.gradle`, `research/lab/build.gradle`, `mcp-server/build.gradle`).
