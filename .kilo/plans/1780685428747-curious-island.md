## 1. Current State — What Already Works

**Critical finding:** The 20-level depth WebSocket path is already operational end-to-end. No transport or WebSocket wiring is needed.

```
DhanTwentyDepthWebSocketClient.onDepthUpdate()
  → DhanWebSocketMultiplexer::publishMarket()
  → MarketDataPipeline.onDepthUpdate()
  → EventBus (Disruptor)
  → GatewayEventBridge.depthPayload() → MARKET_DEPTH
  → Spring WebSocket /ws/gateway
```

**What's already built:**
- Dhan 20-level depth WebSocket with binary parser (`DhanTwentyDepthWebSocketClient`)
- `DepthUpdateEvent` domain event — `record(metadata, symbol, segment, bids, asks, levels, exchangeTimestampMs)` at `core/.../DepthUpdateEvent.java`
- `DepthLevel` record — `record(pricePaisa, quantity, orderCount)` at `core/.../DepthLevel.java`
- `DepthUpdateFactory` — produces `DepthUpdateEvent` from `MarketTickEvent` when depth is present (hotpath module)
- `GatewayEventBridge.depthPayload()` — serializes `DepthUpdateEvent` → JSON on `MARKET_DEPTH` topic (bridge line 257-265)
- `GatewayTopic.MARKET_DEPTH(1, 2)` — already wired in enum (wireId=1)
- `MarketDataPipeline.onDepthUpdate()` — accepts standalone `DepthUpdateEvent` and pushes to EventBus
- `DhanMarketDepthProvider` — **empty stub class** (exists but unimplemented)
- `DepthImbalanceStrategy` — **already implemented** as `GraphStrategyPlugin` with bid/ask ratio, cooldown, and signal generation (`trading/strategy/.../DepthImbalanceStrategy.java`)
- Frontend `terminalStore.ts` already has `depthBySymbol: Record<string, MarketDepth>` and `setDepth(depth)` setter

**What's missing:**
- `OrderBookEngine` (empty stub) — per-symbol state across updates
- S/R, Iceberg, Absorption analytics engines (only Imbalance exists via `DepthImbalanceStrategy`)
- `HeatmapRecorder` — rolls depth snapshots into heatmap chunks
- New WebSocket topics for analytics data (IDs 11–16)
- REST endpoints for initial state hydration
- Canvas DOM screen + heatmap on frontend
- `DhanMarketDepthProvider` — populated with REST snapshot reader from `OrderBookEngine`

## 1.1 Important Corrections from Initial Analysis

### `sequenceId` is NOT a bug (§4.5 removed)

The `DomainEvent` interface provides default methods that delegate to `metadata()`:

```java
// core/.../DomainEvent.java lines 23-28
default long sequenceId() {
    return metadata().sequenceId();
}
default String correlationId() {
    return metadata().correlationId();
}
```

Therefore `depth.sequenceId()` in `GatewayEventBridge` line 265 and `depth.correlationId()` in `DepthImbalanceStrategy` line 126 are both **valid compile-time calls** — no fix needed. The original plan's §4.5 "gate #1" was a false positive.

### `application-dev.yml` already exists

The plan originally listed "Create `application-dev.yml`" as a step. This file already exists at `app/src/main/resources/application-dev.yml` with Dhan sandbox config, scan profiles, and storage paths. **No action needed.**

### `terminalStore.ts` already has depth state

The frontend store already declares `depthBySymbol: Record<string, MarketDepth>` and `setDepth(depth)`. The plan's §2.3 step 17 should note this is already done.

### `BrokerComposition` uses deprecated factory

`BrokerComposition.create()` calls the deprecated `DhanBrokerConnection.create(settings, idempotencyCache)` convenience factory. The multi-adapter constructor (the DI-friendly one) is available but unused in the composition path. This is not blocking for DOM analytics but is a known tech debt item.

### Vite proxy NOT configured

`frontend/vite.config.ts` currently has no `server.proxy` section. This is still needed.

### 4.3 EventBus Wiring Pattern

The analytics pipeline publishes new domain events back onto the same EventBus. The `GatewayEventBridge` subscribes these the same way it subscribes `DepthUpdateEvent`:The bridge self-subscribes via `GatewayEventBridge.register(EventBus)` — the same method that already registers `DepthUpdateEvent.class`. Add analytics event types there:

```java
// In GatewayEventBridge.register(), add:
eventBus.subscribe(DepthImbalanceSnapshot.class, this::onDomainEvent);
eventBus.subscribe(HeatmapChunk.class, this::onDomainEvent);
eventBus.subscribe(IcebergSignal.class, this::onDomainEvent);
eventBus.subscribe(AbsorptionSignal.class, this::onDomainEvent);
eventBus.subscribe(SRLevelsUpdate.class, this::onDomainEvent);
```

Then extend the `onDomainEvent` switch-case to route each to the appropriate `GatewayTopic`:

```java
case DepthImbalanceSnapshot imbalance ->
    router.publish(GatewayTopic.DEPTH_IMBALANCE, writeJson(imbalancePayload(imbalance)));
case HeatmapChunk chunk ->
    router.publish(GatewayTopic.HEATMAP_CHUNK, writeJson(heatmapPayload(chunk)));
// ... etc
```

`DepthAnalyticsPipeline` has an `EventBus` injected — it calls `eventBus.publish(icebergSignal)` etc. on detection. The bridge picks these up and routes them to WebSocket clients.

### 4.4 `DhanMarketDepthProvider` — REST Snapshot Role

The empty stub at `broker/dhan/depth/DhanMarketDepthProvider.java` needs to be populated. Two options:

**Option A: Implement a new `DepthSnapshotProvider` port** (cleaner, avoids bloating `MarketDataProvider`):
```java
// broker/api/port/DepthSnapshotProvider.java (new port)
public interface DepthSnapshotProvider {
    OrderBookSnapshot getSnapshot(String symbol, ExchangeSegment segment, int levels);
}
```
```java
public class DhanMarketDepthProvider implements DepthSnapshotProvider {
    private final OrderBookEngine engine;

    @Override
    public OrderBookSnapshot getSnapshot(String symbol, ExchangeSegment segment, int levels) {
        return engine.getBook(symbol).toSnapshot(levels);
    }
}
```

**Option B: Implement `MarketDataProvider.getDepth()`** (if the port already defines it).

Choose based on whether `MarketDataProvider` already has a depth-read method. Either way, the provider reads from `OrderBookEngine` and serves the REST endpoints. Not involved in WebSocket ingestion.

## 7. Design Decisions

1. **EventBus is the integration point** — `OrderBookEngine` subscribes to `DepthUpdateEvent` alongside `GatewayEventBridge`. No new transport, no new classes in the WebSocket path. Single consumer-registration line per service.

2. **`DhanMarketDepthProvider` is REST-only** — it implements `MarketDataProvider.getDepth()`. It does NOT handle WebSocket ingestion (that flows through EventBus already).

3. **Analytics events travel the same EventBus** — `IcebergDetector` publishes `IcebergSignal` to the same `DomainEventBus`. The bridge subscribes it. No new queue, no new thread pool.

4. **Canvas 2D API, no library** — 2D rectangles + text + gradients are native to browsers. Zero npm dependency cost.

5. **WebSocket for streaming, REST for hydration** — no WebSocket replay needed. Each new panel opens → REST fetch → render → switch to WebSocket.

6. **Incremental mock replacement** — each component is replaced independently. The system always has a working frontend at every step.

7. **Dhan-only for 20-depth** — Upstox and ICICI don't have 20-level feeds. The `OrderBookEngine` API is broker-agnostic but only Dhan produces depth events today.

8. **`DepthImbalanceStrategy` reuse question** — The existing `GraphStrategyPlugin` already computes imbalance ratios and generates signals. Decide early whether the analytics overlay reuses this (via a shared state store) or computes its own view model. The strategy plugin focuses on signal generation; the analytics overlay focuses on visualization state. They can coexist.

9. **`sequenceId` is NOT a gate** — `DomainEvent` provides `sequenceId()` and `correlationId()` as default methods delegating to `metadata()`. No fix required.

10. **`BrokerComposition` tech debt** — The composition factory uses the deprecated `DhanBrokerConnection.create()`. Migrating to the multi-adapter constructor should happen after the DOM analytics work, not before.
